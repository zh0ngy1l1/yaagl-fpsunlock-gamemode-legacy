These are focused offline tests for the installed Wine data-page invalidation defect. They execute the actual helper body extracted from the matching downstream `0001-ntdll-CW-HACK-18947.patch` at riverfog7/macports-wine commit `0bf32337c0c2d2a699fc392f5db570cf42ca0f27`, then apply the submitted source correction patch to that helper with exact context and no fuzz. The corrected helper compiled into the fixture therefore comes from the implementation patch, with an additional check that its only changes are the two reviewed `info.AllocationProtect` references becoming `info.Protect`.

Run with native host Python and C compiler:

```sh
FPS_EVIDENCE_ROOT="$HOME/Library/Application Support/YAAGL Local Builds/genshin-fps360-20260909"
python3 run_offline.py \
  --comparison "$FPS_EVIDENCE_ROOT/automatic160-crash-analysis/revalidation-20260910/companion-review/RUN-TRACE-COMPARISON.json" \
  --output /tmp/yaagl-current-protection-offline-tests
```

`--comparison` and `--output` are required. `--patch` defaults to the vendored hash-pinned downstream patch; `--correction` defaults to the submitted sibling source patch. The original downstream patch has an exact SHA-256 admission check; both original and submitted correction hashes appear in the result. `--comparison` names the existing `RUN-TRACE-COMPARISON.json`; it is a read-only index of the four historical trace paths and hashes. All outputs go into the chosen output directory. Compilation enables AddressSanitizer and UndefinedBehaviorSanitizer. Nothing imports or starts Wine, Genshin, the companion, the launcher or the observer; the fixture creates no remote process and changes no operating-system memory protection.

The key regression is a constructed interleaving: successful four-byte data write, successful target query (`AllocationProtect=0x80`, current `Protect=0x08`), then a game read during the first protection change if present. The original helper requests PAGE_NOACCESS and both the FPS-field read and neighboring eight-byte read fail in the mock page model. Its restoration succeeds and the original write status remains successful. The corrected helper makes no protection call for this page, so both modeled reads succeed. The neighbor bytes are never part of the write. This happens for every distinct integer 61–360, including a game reset and exact-target reapplication.

Each target also tests an early update from the game's disk initializer sentinel −1, without asserting readiness. The intended product composition uses the unchanged protected frontend and original release companion (`8543f45a…`), which does not use d23's experimental first-60/foreground gate. The archived automatic and manual traces remain useful write/page inputs; their replay is not a complete execution replay of the release companion. The generic native helper also preserves distinct scalar payloads 0–60. Zero is a generic data fixture, not a valid enabled launcher target. Root validation separately reused the existing packaged launcher cases: disabling unlocking omits the companion; enabled targets 1–60 still launch it with the exact numeric target, and both game and companion renderer configuration receive that target. Those frontend semantics are unchanged.

The target metadata layout is asserted at compile time: 48-byte x64 MBI, AllocationProtect at offset 16, Protect at offset 36. The exact installed disassembly independently passes the target handle (`r14`) into the query helper at `0x66c5e`. The matching helper's remote branch sends an APC at `0x650b0`; it populates current protection at MBI+0x24 and allocation protection at MBI+0x10. The fixture asserts that every query and protection call receives the supplied target handle.

Executable-page behavior is unchanged when current and allocation protection agree. When they differ, the correction intentionally changes eligibility to reflect the current page. Both mismatch directions are covered: allocation executable/current writable data (`0x80`/`0x08`) no longer toggles, while allocation read-write/current executable-read (`0x04`/`0x20`) now receives the intended invalidation. Current executable protections retain their own modifier bits when deriving the temporary protection; this may also differ from the old allocation-derived request.

The helper source is real; native interfaces are deterministic mocks. The surrounding server-write/status wrapper and scheduling are models of the matching source/disassembly. They are not a compiled Wine server, Mach implementation, Rosetta translator or full companion. Protection modifiers are verified as requested/restored values, without claiming that every modifier combination is accepted by actual NtProtectVirtualMemory. The test retains the original code's ignored restoration failure on actual executable pages as an explicit failing safety scenario, demonstrating that the narrow data-page correction does not fix that separate problem. First-protection failure would make the original uninitialized `origprot` behavior unsuitable for a defined C regression; it is documented rather than fabricated into a deterministic success. Multi-region writes and actual thread/APC timing are outside this four-byte field regression.

The replay reads the four original archives, verifies their hashes, preserves complete recorded read order as run-length encoded inputs, and passes all ten recorded successful writes plus the same-operation pre-write page samples into both helper variants. The original emits twenty modeled protection calls; the correction emits none. The forced interleaving exposes the legacy risk even in surviving runs. It does **not** claim those runs crashed or that either historical exception is proven to occur inside the pulse. Original survival/crash and interval verdicts remain unchanged. Pre-write samples are not the helper's unrecorded query or fault-time page state.

The changed runtime has no target-number branch. The 300-target checks verify exact payload preservation and corrected page behavior, not rendered FPS or gameplay reliability. Disabled-unlocker noninvocation, enabled ≤60 target forwarding/rendering, default 120, maximum 360, per-game Wine/prefix selection, saved preferences, ownership and cleanup are unchanged by the runtime correction and belong to the existing launcher checks. Do not use this fixture's results as evidence that those separate frontend paths were exercised here.
